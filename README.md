# Orqent

Orqent is a multi-tenant visual workflow automation platform for building,
publishing, and inspecting durable AI workflows. The product has two main
surfaces:

- a FastAPI backend that owns authentication, tenancy, workflow validation,
  publishing, triggers, queued execution, node state, documents, embeddings,
  and AI/tool execution;
- a React/Vite frontend for login, workflow authoring, node configuration,
  knowledge ingestion, publishing, run inspection, and operational debugging.

The runtime is the product. FastAPI is the HTTP edge, React is the authoring
surface, LangChain is isolated behind an adapter, MySQL is the authoritative
store, and Chroma is a derived tenant-scoped vector index.

## Capabilities

- Authentication with access and refresh tokens.
- Tenant-scoped workflow authoring with drafts, optimistic revisions,
  validation, and immutable published versions.
- Visual DAG semantics with typed handles, branching, merge, skipped paths,
  suspension, and resume.
- Code-defined node catalogue exposed at `/api/v1/node-types`.
- Manual, webhook, and schedule triggers.
- Durable MySQL-backed queue, worker, and schedule dispatcher.
- Run, node execution, and event inspection.
- Gemini AI agent execution through the LangChain adapter boundary.
- Document ingestion, embeddings, Chroma retrieval, and tenant-scoped RAG.
- Provider-neutral tool calling with the calculator tool.

## Architecture

```text
Browser (React/Vite)
  -> FastAPI API (/api/v1, /hooks, /health)
      -> MySQL: users, organizations, workflows, versions, runs, queue, events
      -> Worker: claims queue tasks and executes ready nodes
      -> Dispatcher: turns due schedules into queued runs
      -> Gemini: reached only by backend worker code through LangChain
      -> Chroma: derived vector index for tenant-scoped retrieval
```

Important boundaries:

- The browser talks only to Orqent. It does not call Gemini, Chroma, or MySQL.
- `GEMINI_API_KEY` is server-side only and optional at startup. Non-AI flows
  work without it; AI node execution fails clearly if the provider key is absent
  or quota is unavailable.
- LangChain imports are confined to `src/app/infrastructure/llm/`.
- Organization and tenant identity are derived from the authenticated user, not
  authored in frontend requests.
- Webhook tokens are bearer credentials. They are generated by publishing a
  webhook-triggered workflow, shown once by the frontend, and stored server-side
  only as digests.

## Prerequisites

- Python 3.12+
- Node.js and npm
- Docker with Docker Compose

## Backend Setup

Create a virtual environment and install the backend with development tools:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

Create local configuration:

```bash
cp .env.example .env
```

For host-based development, `.env.example` points at MySQL on
`127.0.0.1:3306` and Chroma on `127.0.0.1:8001`. Generate and set
`APP_JWT_SECRET_KEY` before running the API directly:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

To run AI workflows, export `GEMINI_API_KEY` in your shell or put it in the
repo-root `.env`. Do not put provider keys in `frontend/.env.example` or any
`VITE_*` variable.

## Running Locally

Full stack through Compose:

```bash
docker compose up --build
```

This starts:

- API on `http://localhost:8000`
- worker process for queued runs
- schedule dispatcher
- MySQL on `localhost:3306`
- Chroma on `localhost:8001`

Hybrid host development:

```bash
docker compose up -d mysql chroma
source .venv/bin/activate
alembic upgrade head
uvicorn app.main:app --reload
```

Health and OpenAPI:

- Liveness: `GET http://localhost:8000/health/live`
- Readiness: `GET http://localhost:8000/health/ready`
- Interactive API docs: `http://localhost:8000/docs`

The versioned product API mounts at `/api/v1`. Public webhook deliveries mount
at `/hooks/{token}`.

## Frontend Setup

Install and run the frontend from `frontend/`:

```bash
cd frontend
npm install
npm run dev
```

The frontend uses one public client setting:

```bash
cp .env.example .env
```

`VITE_API_BASE_URL` should point at the backend, normally
`http://localhost:8000`. Every `VITE_*` value is compiled into the browser
bundle, so it must never contain secrets.

Useful frontend commands:

```bash
npm run lint
npm run build
npm run preview
```

## Database Migrations

Alembic reads `APP_DATABASE_URL` through backend settings.

```bash
source .venv/bin/activate
alembic upgrade head
alembic current
```

The current migration series includes authentication, refresh tokens, workflow
authoring, execution, queue tasks, trigger registrations, schedules, and
documents.

## API Surface

Current route groups:

- `/api/v1/auth` - register, login, refresh, logout, current user
- `/api/v1/workflows` - list, create, update, draft graph, validate, publish,
  versions
- `/api/v1/node-types` - runtime node catalogue
- `/api/v1/runs` - create, list, inspect, advance, resume, events
- `/api/v1/documents` - ingest or replace one document in the caller's corpus
- `/hooks/{token}` - unauthenticated public webhook delivery by bearer token
- `/health/live` and `/health/ready` - process and dependency health

## Example Workflows

Manual AI run:

```text
trigger.manual -> ai.agent -> core.log
```

Configure the AI Agent with instructions, the default model profile,
temperature, optional retrieval with `top_k`, and optional calculator tool
access. Ingest policy or knowledge text first if retrieval is enabled.

Branching:

```text
trigger.manual -> core.condition
core.condition:true  -> core.noop -> core.merge
core.condition:false -> core.noop -> core.merge
```

Condition outputs use named handles. Untaken branches are recorded as skipped
so the run inspector can show what happened.

Webhook:

```text
trigger.webhook -> ai.agent -> core.log
```

Publish returns a one-time webhook token. Use the full `/hooks/{token}` URL as
the delivery target in the external system.

Schedule:

```text
trigger.schedule -> ai.agent -> core.log
```

Schedule trigger configuration uses cron syntax. Local frontend copy marks the
cron as UTC.

## Security Notes

- Keep backend secrets in the repo-root `.env` or deployment secret manager.
- The frontend only needs `VITE_API_BASE_URL`.
- Never expose `GEMINI_API_KEY`, `APP_DATABASE_URL`, `APP_JWT_SECRET_KEY`, or
  webhook tokens in browser code, logs, localStorage, or built assets.
- Access tokens are short-lived bearer tokens. The frontend keeps the access
  token in memory and persists only the refresh token needed for reloads.
- Backend errors, AI output, and document content should render as escaped text
  in React, not HTML.
- Chroma data is derived from MySQL document/chunk state. MySQL remains the
  source of truth.

## Deferred Work

The current app intentionally does not include document listing/deletion, file
uploads, citations, analytics, billing, OAuth, team management, collaborative
editing, WebSockets/SSE, templates, or external side-effecting tools such as
email senders. Those are product follow-ups, not prerequisites for the current
demo path.
